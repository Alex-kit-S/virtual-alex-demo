# /prompting - Plain English In, Senior-Level Prompt Out

Spec: work/26-prompting/CLAUDE.md (read it first; it defines the flow, the two prompt layers, the file lookup table, the task patterns, and the hard-case behaviors). Model layer: work/26-prompting/model-playbook.md (Anthropic's per-model prompting guidance, the file the spec points at). On-demand. Alex acts as a senior prompt engineering specialist: the owner speaks intent, Alex hands back a lean CONTEXT / INPUT / OUTPUT prompt for Claude Code.

Usage: `/prompting` (or with the request inline: `/prompting I want a workflow that watches my Gmail...`), or just say "write me a prompt for...".

**Two jobs, not one.** Building a NEW prompt takes the nine steps below. **Repairing an existing one** ("fix this prompt", "why did this prompt fail", a pointer at a file in outputs/prompting/) takes the spec's repair flow instead: read the original in full, diagnose and name the evidence before editing, default to a targeted diff rather than a rebuild, preserve the original `Built for:` unless told otherwise, re-check against today's rules, and save the repair as a NEW dated artifact so the original survives as evidence.

## Steps (condensed; spec is authoritative; renumbered 1-9 on 2026-08-26 so the order is one a run can actually follow)
1. **Extract intent** (voice input arrives messy; take it as-is, never ask for a repeat). A non-text request (screenshot, PDF, .pptx, sheet) gets read with its bound skill FIRST.
2. **Identify task type, lifetime, and target harness.** Type from the spec's patterns; one-off vs durable; and WHERE it runs, a Claude Code session (default, full universal layer) or a scheduled `claude -p` wrapper (same layer, model pinned, unattended already answered).
3. **The overlap check, first among the checks.** Request vs the routing table / system/manifest.json. Substantially covered by an existing automation -> flag it in the gap round: extend or build new? the owner decides. Never silently rebuild a live system. **An "already covered" answer ends the run with NO prompt:** name the automation that covers it, point at its command file and spec, offer to fix the part falling short, log it as `routed`, and do not increment the prompt count. A correct run does not always produce a prompt.
4. **Resolve BOTH models (split in two on 2026-08-26; they are not the same question).** The **EXECUTOR** is what runs the prompt you hand over, and it is what `Built for:` and `Suggested effort:` mean. The **ARTIFACT** is what the thing the prompt builds runs on, here only a scheduled wrapper pinned in `system/manifest.json` `meta.model_routing.local_wrappers`; V13 enforces that pin, so state it and never ask it, and no answer can override it. Executor order, stop at the first that applies: (a) the prompt IS what a pinned wrapper runs, so both are fixed by the contract, state it; (b) the owner named one, use it, and if it contradicts the artifact pin say both in one line, the contract wins for the artifact and the owner's answer for the executor; (c) otherwise **ASK, every time** via AskUserQuestion, `Opus 5` (default, what an interactive session runs) or `Fable 5`, Other for Sonnet 5 / Haiku / a 4.x. The question rides as the FIRST question of the single gap round, and **that round fires even when the model is the only gap.**
5. **Build the step sequence** from the task patterns in the spec. No permission-asking.
6. **Gap-check** (both models, attended or unattended, format, destination, MCPs, what the output ENABLES, whether the shape needs 2-5 `<example>` blocks, one-off vs durable, overlap resolution). A needed MCP that is not installed at all gets said out loud with its fallback, never written into a step. **ONE batched round of questions in chat**, only real gaps, always ending with: "or say *defaults*."
   **Premise check, before the gap round closes.** A request can be clear, specific and still ask about something its subject does not have, usually because a named standard, format or tool governs a different layer than the request assumes. That is not a gap to fill, it is a premise to correct, and executing it literally produces a confident answer to the wrong question. When the premise looks wrong: say so in one sentence, offer the in-category version of the same question, and put BOTH in the gap round so the owner rules. Never silently substitute your own version, and never execute a question you believe is malformed without flagging it. Check the cost of the answer too: if a source the request names is paywalled, login-walled or otherwise unreadable, the run can retrieve titles and status from it but not content, so say that before it is built into a step.
   **A partially answered round is normal.** One answer out of three is a register, not an oversight. Do NOT open a second round: apply defaults to the rest and SAY which ones you applied, in one line, before delivering. A default the owner can see is one they can correct; a silent default is how a pin already fixed by contract gets quietly discarded.
7. **Re-resolve, then assemble** per the spec's structure. The round's answers can move the target, so re-run step 4 against the resolved target first and say so in one line if the executor changed. **Universal layer, every prompt:** INPUT 1 = Identity (re-read the loaded soul core; pull full soul.md only when the task's register is not in the card; CLAUDE.md wins on conflict), INPUT 2 = Resources opening verbatim with "Identify the skills that are needed for the task and use them" + the resolved, NAMED skills/MCPs/file pointers, INPUT 3 = pattern steps. When a paste is present at all and you are unsure of its size, put it ABOVE the three headers in `<document>` tags with the ask last (playbook 2.6, up to 30 percent better) and add a quote-first instruction; the ~20K-token figure is a floor, not a gate, and nothing here counts tokens. OUTPUT 1 states the deliverable **and its length** ("match the length to what the task needs, no filler sections, no redundant summaries, no boilerplate"; name a real band where one exists). OUTPUT ends with the real Close-Out Gate reference, never a paraphrase. Pointer style throughout: reference files, never restate their contents.
8. **Then swap in the resolved model's addendum** from the spec's model layer. This is the half that is NOT universal: two of its lines invert between models and one substitutes. Opus 5 gets the scope line ("deliver this task at the scope asked..."), the conciseness line, the corrections and progress lines, and the delegation cap (never a subagent to verify work already finished). Fable 5 gets the boundaries block, the anti-over-engineering block, the lead-with-the-outcome line, the grounded-progress block, and delegation turned UP rather than capped. Never ship one model's lines under the other's label. **If the resolved model has no playbook section at all, STOP:** build on the universal layer only, name the missing section, and ask whether to proceed or wait for a refresh. Never fall back to the Opus 5 block, which is exactly what makes a wrong-model prompt look right. Research still routes through /research-team on every model, and a relay the owner dictated is exempt from every delegation rule.
9. **Deliver lean:** one markdown block, three headers, zero padding, 400 to 900 words (say in one line if a genuine multi-phase relay needs more). Save to outputs/prompting/YYYY-MM-DD/{slug}.md, keeping a POINTER to any pasted source that has a path rather than the paste itself. One line rides OUTSIDE the block **and is written into the saved file too**: `Built for: <executor model> - Suggested effort: <low|medium|high|xhigh|max>`, the effort taken from the resolved model's row and never carried across from another model. Then **offer once:** "run it now?" Yes -> execute in this session as Alex. If the resolved model is not what this session runs, say so in one line first.

## Hard constraints
Overlap check always first · **both models resolved before assembly, the executor asked every time it is unstated** · one gap round max, defaults skip always offered, defaults applied out loud · the verbatim skills sentence in every INPUT · MANDATORY skill bindings named, never generic · pointer style, no retyped facts · real gates referenced, never paraphrased · lean delivery inside the word band, no padding · durable automations route through /new (registry-first, and that holds even when it runs now) · **the model-layer lines come from the resolved model's block, never applied unconditionally** (a model-layer rule applied to every model is a bug with a delay on it, and it stays invisible because the prompt still reads well) · **verification hygiene: no generic "verify your work" step ever; verification only as an external-system read-back, a pixel/render check, or a named gate** (Opus 5 self-checks; a blanket instruction just pays twice). The one model-dependent exception: on Fable 5 a NAMED fresh-context verifier subagent at a stated interval is allowed on long runs (playbook 4.12), because a mechanism with a target is not a blanket instruction.

## Post-Run
- Update vault/projects/prompting/status.md (last_run, runs, prompt pointer, model built for) + vault/log.md `## [YYYY-MM-DD HH:MM] prompting | {slug}, {task type}, {executor model}, {delivered|delivered+ran|routed}`.
- **Run `node scripts/prompt-regression-check.js --delivered`** on this run's own artifact before closing. The function checks its own output; a shape it just broke should surface now.
- New pattern built from first principles? Append it to the spec's Task patterns section.
- Close-Out Gate per root CLAUDE.md.
